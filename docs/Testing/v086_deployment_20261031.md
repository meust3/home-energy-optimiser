## Deployment gates

1. Preserve existing work and protected App configuration. Verify the exact remote
   release commit and passing CI, build the standard amd64 image, check installed
   source/dependencies and run offline bootstrap checks. Publish an immutable new
   `v0.8.6` tag; never move `v0.8.5`.
2. Take a fresh consistent read-only production backup and verify its checksum and
   isolated PostgreSQL 17 restore against matching snapshot counts. Retain owners,
   ACL requirements and original private backup evidence outside Git.
3. On the isolated current-data copy, verify v0.8.6 startup/readiness, bounded
   analytical scoring and complete pending-inventory reconciliation using a
   non-superuser role matching production ownership. Rehearse App rollback to
   v0.8.5 on the same schema. Compare historical data before intentional scoring.
4. Check current production permissions without changing grants unnecessarily.
   Preflight shows `energy_app` owns the queue and historical tables and is not a
   superuser/role creator/database creator. Verify DML/function permissions and
   enabled trigger/index invariants; a historical fixture is not live evidence.
5. Verify recoverable App backup/options and current storage health. Use the supported
   Home Assistant App update path, keeping its rollback-backup option enabled.
   Stop analytical writers only for the controlled cutover; record actual gaps.
   **Do not run Alembic upgrade/downgrade or change schema stamps in production.**
6. Install v0.8.6, compare protected options, and verify health, Ingress, continuous
   five-minute collection and two natural forecast/reserve/HOLD cycles. No manual
   calculations, integrations or hardware actions are acceptance shortcuts.

## Recovery

If App acceptance fails, stop the candidate and restore the retained v0.8.5 App
and original protected options on unchanged schema `20261024_01`. Verify startup,
collection and normal forecast operations. Preserve any new observations/scores;
do not restore an older database over later data or downgrade the inventory to
recover an App-only update. Database restoration requires separate data-loss review.
